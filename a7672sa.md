# SIMCom A7672SA — referência de recursos e comandos AT

Resumo prático do conjunto **A76XX AT Command Set** aplicado ao A7672SA, na mesma
ordem dos painéis da interface. Comandos marcados com ⚠ variam conforme a revisão
de firmware — confirme com `AT+SIMCOMATI` e com o manual da sua build.

---

## 1. O que o chip tem (e o que não tem)

| Recurso | Situação no A7672SA |
|---|---|
| LTE Cat.1 bis (FDD) | B1 / B2 / B3 / B5 / B7 / B8 / B28 — ~10 Mbps DL, 5 Mbps UL |
| GSM / GPRS / EDGE | 850 / 900 / 1800 / 1900 MHz (fallback 2G) |
| GNSS | GPS, GLONASS, BeiDou, Galileo — presente nas variantes **-FASE** (o sufixo `L…` não traz GNSS) |
| Voz | VoLTE e CS voice, DTMF, PCM digital, codecs via `AT+CSDVC` |
| SMS | Texto e PDU, memória SIM/ME |
| Dados | TCP/UDP (10 sockets), HTTP(S), MQTT(S), FTP(S), SMTP, SSL/TLS |
| Filesystem | `C:/` interna (certificados, uploads) |
| Interfaces | UART (padrão **115200 8N1**), USB 2.0, I²C, SPI, ADC, GPIO, PCM |
| **Bluetooth** | **Existe** — clássico com perfil SPP. Sem BLE/GATT. Ver seção 13 |
| **Wi-Fi** | Não existe neste módulo |

Alimentação: 3.4–4.2 V (típico 3.8 V), picos de corrente de ~2 A em TX — fonte fraca
é a causa nº 1 de reset durante registro na rede.

## 2. Identificação

| Comando | Resposta / uso |
|---|---|
| `AT` | `OK` — teste de sanidade |
| `ATE0` / `ATE1` | desliga/liga o eco do comando |
| `AT+CMEE=2` | erros em texto (`+CME ERROR: SIM not inserted`) |
| `ATI` | modelo, ex. `A7672SA-FASE` |
| `AT+SIMCOMATI` | fabricante, modelo, revisão, IMEI em bloco |
| `AT+CGMR` | versão de firmware |
| `AT+CGSN` | IMEI |
| `AT+CIMI` | IMSI do SIM |
| `AT+CICCID` | ICCID (`+ICCID: 8955…`) — note que **não** é `AT+CCID` como no SIM808 |
| `AT+CNUM` | número do assinante (se gravado no SIM) |
| `AT+CPIN?` | `+CPIN: READY` / `SIM PIN` / `SIM not inserted` |
| `AT&W` | grava o perfil atual |

## 3. Rede LTE / GSM

| Comando | Uso |
|---|---|
| `AT+CFUN=0/1/4` | rádio off / full / modo avião; `AT+CFUN=1,1` reinicia |
| `AT+CNMP=<n>` | preferência: `2` auto, `13` só GSM, `38` só LTE, `51` GSM+LTE |
| `AT+CNSMOD?` | modo em uso: `8` = LTE, `3` = EDGE, `1` = GSM |
| `AT+CREG?` / `AT+CGREG?` / `AT+CEREG?` | registro CS / GPRS / EPS — `,1` local, `,5` roaming |
| `AT+COPS?` | operadora e tecnologia atual (`,7` = E-UTRAN) |
| `AT+COPS=?` | varredura de operadoras (até ~60 s, bloqueia a porta) |
| `AT+COPS=0` | volta ao registro automático |
| `AT+CSQ` | `+CSQ: <rssi>,<ber>` — dBm = `-113 + 2·rssi` |
| `AT+CESQ` | `+CESQ: rxlev,ber,rscp,ecno,rsrq,rsrp` — RSRP dBm = `-140 + idx`, RSRQ dB = `-19.5 + 0.5·idx` |
| `AT+CPSI?` | a leitura mais completa: modo, MCC-MNC, TAC, Cell ID, PCID, banda, EARFCN, RSRQ, RSRP, RSSI, SINR (RSRP/RSSI vêm em décimos: `-850` = −85,0 dBm) |
| `AT+CGDCONT=1,"IP","<apn>"` | define o APN |
| `AT+CGAUTH=1,1,"user","pass"` | autenticação PAP quando a operadora exige |
| `AT+CGATT=1` / `AT+CGATT?` | anexa ao serviço de pacotes |
| `AT+CGPADDR` | IP do contexto PDP |

APNs comuns no Brasil: `claro.com.br`, `zap.vivo.com.br`, `tim.br`, `gprs.oi.com.br`,
`virtueyes.com.br` / `iot.datora.com.br` para chips M2M.

## 4. GNSS

Diferente do SIM808 — os comandos mudaram de nome:

| SIM808 | A7672SA |
|---|---|
| `AT+CGNSPWR=1` | `AT+CGNSSPWR=1` |
| `AT+CGNSINF` | `AT+CGNSSINFO` |
| `AT+CGNSURC=n` | `AT+CGNSSTST=1` (stream NMEA) ou polling do app |

| Comando | Uso |
|---|---|
| `AT+CGNSSPWR=1` | liga o receptor; responde `OK` e depois a URC `+CGNSSPWR: READY!` |
| `AT+CGNSSMODE=<n>` ⚠ | seleção de constelações (o mapeamento varia por firmware; 3 costuma ser GPS+GLONASS) |
| `AT+CGNSSINFO` | posição atual |
| `AT+CGNSSNMEA=1,1,1,1,1,0,0,0` | quais sentenças NMEA serão emitidas |
| `AT+CGPSNMEARATE=1` | 1 Hz |
| `AT+CGNSSTST=1` | envia o NMEA para a porta AT |
| `AT+CGNSSPORTSWITCH=0,1` | direciona o NMEA para a porta AT em vez da porta dedicada |
| `AT+CGPSHOT` / `AT+CGPSWARM` / `AT+CGPSCOLD` | reinícios do receptor |
| `AT+CAGPS` | baixa assistência da SIMCom (exige dados ativos) — reduz muito o TTFF |

Formato da resposta:

```
+CGNSSINFO: <mode>,<GPS-SVs>,<GLONASS-SVs>,<BeiDou-SVs>,
            <lat>,<N/S>,<lon>,<E/W>,<ddmmyy>,<hhmmss.s>,
            <alt>,<speed_kn>,<course>,<PDOP>,<HDOP>,<VDOP>
```

Sem fix, todos os campos vêm vazios: `+CGNSSINFO: ,,,,,,,,`.
Latitude/longitude vêm em **ddmm.mmmmmm** (NMEA), não em graus decimais — a
interface faz a conversão (`grau = dd + mm.mmmm/60`).

## 5. SMS

```
AT+CMGF=1                 modo texto
AT+CSCS="GSM"             ou "UCS2" para acentos/emoji (número e texto em hex UTF-16BE)
AT+CPMS="SM","SM","SM"    memória do SIM
AT+CNMI=2,1,0,0,0         URC +CMTI ao receber
AT+CMGS="+5511999999999"  aguarda '>' e termina com Ctrl+Z (0x1A)
AT+CMGL="ALL"             lista; "REC UNREAD" apenas não lidas
AT+CMGR=<i>               lê índice
AT+CMGD=,4                apaga tudo
```

## 6. Voz e áudio

```
ATD+5511999999999;   chamada de voz (o ';' final é obrigatório)
ATA / AT+CHUP        atender / encerrar
AT+CLCC              chamadas ativas
AT+CLIP=1            identificação do chamador nas URCs
AT+VTS="1"           envia DTMF
AT+CLVL=<0..5>       volume de saída
AT+CSDVC=<1|2|3>     handset / headset / speaker
AT+CMUT=1            muta o microfone
AT+CPCMREG=1  ⚠      habilita a interface PCM digital
```

URCs relevantes: `RING`, `+CLIP:`, `NO CARRIER`, `BUSY`, `NO ANSWER`, `MISSED_CALL:`.

## 7. TCP / UDP

```
AT+NETOPEN                      abre o stack IP  → +NETOPEN: 0
AT+IPADDR                       IP local
AT+CIPOPEN=0,"TCP","host",4242  abre socket 0    → +CIPOPEN: 0,0
AT+CIPSEND=0,<len>              aguarda '>' e envia exatamente <len> bytes
AT+CIPCLOSE=0                   fecha socket
AT+NETCLOSE                     fecha o stack
AT+CIPRXGET=1                   recepção manual (senão os dados chegam como +IPD<len>)
AT+CDNSGIP="host"               resolve DNS
AT+CPING="8.8.8.8",1,4,64,1000,10000,255
```

## 8. HTTP(S)

```
AT+HTTPINIT
AT+HTTPPARA="URL","https://exemplo.com/api"
AT+HTTPPARA="CONTENT","application/json"     (POST)
AT+HTTPPARA="SSLCFG",0                       usa o contexto SSL 0
AT+HTTPDATA=<len>,10000                      responde DOWNLOAD; envie <len> bytes crus
AT+HTTPACTION=0|1|2|3                        GET / POST / HEAD / DELETE
   → URC: +HTTPACTION: <method>,<status>,<len>
AT+HTTPHEAD                                  cabeçalhos da resposta
AT+HTTPREAD=0,<len>                          corpo (offset 0)
AT+HTTPTERM
```

Diferença importante em relação ao SIM808: aqui o `HTTPREAD` recebe **offset e
tamanho** (`AT+HTTPREAD=0,1024`), e o corpo termina com `+HTTPREAD: 0`.

## 9. MQTT

```
AT+CMQTTSTART                                    → +CMQTTSTART: 0
AT+CMQTTACCQ=0,"clientId",0                      0 = TCP, 1 = SSL
AT+CMQTTSSLCFG=0,0                               vincula o contexto SSL (quando ssl://)
AT+CMQTTCONNECT=0,"tcp://broker:1883",60,1[,"user","pass"]
   → +CMQTTCONNECT: 0,0
AT+CMQTTTOPIC=0,<len>    ... '>' ... tópico
AT+CMQTTPAYLOAD=0,<len>  ... '>' ... payload
AT+CMQTTPUB=0,<qos>,60                           → +CMQTTPUB: 0,0
AT+CMQTTSUB=0,<len>,<qos> ... '>' ... tópico
AT+CMQTTUNSUB=0,<len>,0
AT+CMQTTDISC=0,120 / AT+CMQTTREL=0 / AT+CMQTTSTOP
```

Mensagens recebidas chegam como bloco de URCs:
`+CMQTTRXSTART` → `+CMQTTRXTOPIC` + tópico → `+CMQTTRXPAYLOAD` + payload → `+CMQTTRXEND`.

## 10. SSL/TLS e filesystem

```
AT+CSSLCFG="sslversion",0,4      0=SSL3 1=TLS1.0 2=TLS1.1 3=TLS1.2 4=todas
AT+CSSLCFG="authmode",0,1        0 sem verificação · 1 servidor · 2 mútua
AT+CSSLCFG="enableSNI",0,1       obrigatório na prática — veja a nota abaixo
AT+CSSLCFG="cacert",0,"ca.pem"
AT+CCERTDOWN="ca.pem",<len>      aguarda '>' e recebe o PEM cru
AT+CCERTLIST / AT+CCERTDELE="ca.pem"
AT+FSCD=C:/ · AT+FSLS · AT+FSMEM · AT+FSDEL=<arquivo>
```

**SNI não vem ligado por padrão** — e sem ele qualquer host atrás de CDN ou
virtual host (a maior parte da internet) derruba o handshake. O sintoma é
`+HTTPACTION: <method>,715,0` chegando em ~0,3 s: rápido demais para ser timeout,
porque o TLS nem começou. Medido neste módulo (fw `A7672M7_B19V01_250905`) contra
`https://example.com`:

| `enableSNI` | Resultado |
|---|---|
| `0` | `+HTTPACTION: 0,715,0` em 0,3 s |
| `1` | `+HTTPACTION: 0,200,559` em 2,8 s |

Vale para HTTPS **e** para MQTT sobre TLS — os dois usam o mesmo contexto SSL.

## 11. Hardware, energia e relógio

| Comando | Uso |
|---|---|
| `AT+CBC` | tensão de alimentação (`+CBC: 3.918V`) |
| `AT+CPMUTEMP` | temperatura interna em °C |
| `AT+CADC?` | leitura do ADC em mV |
| `AT+CGDRT=<gpio>,<dir>` | direção do GPIO (0 entrada, 1 saída) |
| `AT+CGSETV=<gpio>,<val>` / `AT+CGGETV=<gpio>` | escreve / lê o GPIO |
| `AT+CCLK?` / `AT+CCLK="aa/mm/dd,hh:mm:ss±zz"` | relógio (fuso em quartos de hora) |
| `AT+CTZU=1` | atualiza o fuso pela rede |
| `AT+CNTP="pool.ntp.org",-12` + `AT+CNTP` | sincronismo NTP (exige dados) |
| `AT+CSCLK=1` | sleep automático (acorda com atividade na UART) |
| `AT+CRESET` | reset por software |
| `AT+CPOF` | desliga o módulo (religa só pelo PWRKEY) |
| `AT+IPREX=115200` | fixa o baud da UART |

## 12. Erros comuns

| Sintoma | Causa provável |
|---|---|
| Módulo não responde a `AT` | baud errado (tente 115200), UART sem nível lógico correto, PWRKEY não pulsado |
| Reset ao registrar na rede | fonte incapaz de sustentar picos de 2 A |
| `+CME ERROR: 3` em HTTP/MQTT | faltou `AT+HTTPINIT` / `AT+CMQTTSTART`, ou o contexto PDP não está ativo |
| `+HTTPACTION: <m>,715,0` em ~0,3 s | SNI desligado — falta `AT+CSSLCFG="enableSNI",0,1` (seção 10) |
| `+CGNSSINFO: ,,,,,,,,` sempre | antena GNSS ausente/mal casada, ou variante sem GNSS (sufixo sem `F`) |
| `AT+CGNSSTST=1` retorna erro | GNSS ainda não foi ligado com `AT+CGNSSPWR=1` |
| Registro só em 2G | banda LTE da operadora fora do suporte, ou `AT+CNMP=13` gravado |
| `AT+BTSCAN=1,20` retorna ERROR | são **três** parâmetros: `AT+BTSCAN=<liga>,<modo>,<segundos>` (seção 13) |

## 13. Bluetooth

Este módulo **tem** Bluetooth, ao contrário do que esta referência afirmava
até agosto/2026. Verificado no hardware (fw `A7672M7_B19V01_250905`): o rádio
liga e a varredura encontra aparelhos reais.

```
AT+BTPOWER?              0 = desligado, 1 = ligado
AT+BTPOWER=1             liga o rádio
AT+BTHOST?               +BTHOST: SIMOCM BT,14:00:20:D5:E2:C7
AT+BTSCAN=1,1,20         varre por 20 s (o range aceito é 6-48)
   → +BTSCAN: 0,1,LG CJ44  (6D),00:1F:47:EE:D9:6D,175
   → +BTSCAN: 1           fim da varredura
AT+BTPAIR=<index>        pareia pelo índice devolvido no scan
AT+BTUNPAIR=<index>      desfaz o pareamento
AT+BTPAIRED?             lista os pareados
AT+BTSPPSEND             envia dados pelo perfil SPP (porta serial)
AT+BTPOWER=0             desliga
```

Formato de cada linha do scan:
`+BTSCAN: <índice>,<tipo>,<nome>,<MAC>,<RSSI>`

**O que esta build NÃO tem** — todos respondem `ERROR`:
`AT+BTCONNECT`, `AT+BTDISCONN`, `AT+BTVISIBILITY`, `AT+BTSPPGET`, `AT+BTGATT`.

Ou seja: **Bluetooth clássico com SPP, sem BLE/GATT**. Para falar com sensores
BLE não serve; para trocar dados com um aparelho pareado por porta serial,
serve.

Duas pegadinhas que custaram tempo aqui:

- `AT+BTSCAN` leva **três** parâmetros. Com dois (`AT+BTSCAN=1,20`) devolve
  `ERROR`, o que faz parecer que o comando não existe.
- O prefixo dos comandos é `AT+BT*`, não `AT+CBT*`. Toda a família `AT+CBTPOWER`
  / `AT+CBTSTATUS` / `AT+CBTPAIR` responde `ERROR` — e testar só ela leva à
  conclusão errada de que o módulo não tem Bluetooth.
